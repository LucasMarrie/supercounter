# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- Install dependencies: `npm install`
- Run the server: `npm start` (or `node server.js`) — serves on `http://localhost:3000` (override with `PORT` env var)
- Requires `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` env vars (a free Upstash Redis database) — set them in a local `.env` file for development, loaded via `dotenv`.
- `RESET_PASSWORD` env var (optional) enables the corner reset control described below. If unset, reset requests are always denied.
- No build step, no test suite, no linter configured.

## Architecture

This is a global counter app: the count lives only on the server, and every client sees updates in real time over a single shared WebSocket connection (no polling, no per-client state).

- **`server.js`** — Express serves the static `public/` folder; a `ws` `WebSocketServer` is attached to the same HTTP server. The counter value is persisted in an Upstash Redis database under the key `supercounter:count` (via `@upstash/redis`'s REST client, `Redis.fromEnv()`). There is no REST API — the increment/decrement/reset actions and the broadcast all go through WebSocket messages.
- **Debounced Redis writes** — increment/decrement mutate the in-memory `count` and broadcast immediately; the Redis write itself is deferred. `pendingDelta` accumulates the net change since the last flush; `scheduleFlush()` resets a `FLUSH_DEBOUNCE_MS` (3s) timer on every change so a quiet period triggers one `redis.incrby()` for the whole burst, capped by a `FLUSH_MAX_DELAY_MS` (10s) timer that doesn't reset, so sustained clicking still flushes periodically instead of starving the debounce indefinitely. This exists specifically to stay well under Upstash's free-tier daily command limit — a burst of rapid clicks now costs one Redis write instead of one per click. `process.on('SIGTERM'/'SIGINT', ...)` flushes on shutdown so a Render redeploy doesn't lose the unflushed tail (Render sends `SIGTERM` before killing a deploy). `reset` is NOT debounced — it's rare enough that batching buys nothing, and it needs to write through immediately since it's an absolute `redis.set()`, not a relative delta; it also clears any pending delta/timers so a stale unflushed increment can't reapply on top of the reset later. One side effect: increment/decrement can no longer fail from the client's perspective (they're pure in-memory mutations now) — only the background flush or a reset can hit a Redis error.
- **WebSocket protocol** (JSON messages):
  - Server → client on connect: `{type: 'init', count}`
  - Client → server on button click: `{type: 'increment', id}` / `{type: 'decrement', id}` — `id` is a client-generated per-request number, used only for the client's own optimistic-UI reconciliation (see below); the server just echoes it back, it has no meaning to the server itself
  - Server → all clients after handling an increment/decrement: `{type: 'update', count, id}` (via `broadcast()`, which iterates `wss.clients`) — `id` is only meaningful to the client that sent that particular request; everyone else ignores it
  - Client → server on reset submit: `{type: 'reset', password, value}`
  - Server → all clients after a successful reset: `{type: 'update', count}` (no `id` — reset isn't part of the optimistic-reconciliation scheme)
  - Server → the requesting client only, on a failed reset (wrong password or non-integer value): `{type: 'reset-denied'}`
  - Server → the requesting client only, if a reset's `redis.set()` throws: `{type: 'error'}`. The deferred flush failing is *not* reported to any client — it's logged server-side and retried on the next scheduled flush; the in-memory `count` and every client's live display are already correct regardless of whether the background flush has caught up.
- **`public/client.js`** — owns the WebSocket lifecycle: connects, reconnects with increasing backoff (capped at 10s) on close/error, and disables the increment button while disconnected. `init` and `update` both retrigger the glow animation via `setCount`. Derives `ws:`/`wss:` from `location.protocol`, so it works unmodified behind TLS in production.
- **Initial load placeholder** — the counter markup starts as an invisible (`opacity: 0`) `&nbsp;`, not empty and not `0` (which would misleadingly imply the real count is zero). The `&nbsp;` reserves the real line-box height immediately, so the box doesn't jump in height once real digits replace it — a genuinely empty element generates no line box at all. `setCount()` removes the `.placeholder` class on the first real value it receives, fading and width-animating it in.
- **`public/style.css`** — the counter number's glow on update is a CSS `@keyframes` animation applied via a class: warm `lavaPulse`/`.lava` when the value increases, cold `frostPulse`/`.frost` when it decreases (mirror-image keyframes, same structure, `--cold-*` palette instead of `--lava-*`). `applyLayout()` in `client.js` picks the class from the same `decreased` comparison already used for the width-shrink logic. Because re-adding the same class doesn't restart a CSS animation, it removes *both* glow classes, forces a reflow (`void counterEl.offsetWidth`), then adds the right one — this is required for consecutive rapid changes to each retrigger the glow. `animation-timing-function` is `linear`, not eased — an eased curve applies separately to *each* keyframe segment (0%→35%→70%→100%), so a strong ease-out there looks like discrete jump-then-freeze steps rather than one continuous motion. Both animations' `text-shadow` keeps exactly 4 layers at every keyframe stop (padding with transparent filler layers where a color doesn't conceptually exist) — browsers can't smoothly interpolate `text-shadow` between keyframes with mismatched layer counts, they just snap.
- **Counter width animation** — `setCount()` in `client.js` measures the counter's pixel width before and after a value change (a FLIP-style transition) and animates the element's explicit `width` CSS property, rather than relying on `ch`-unit estimates (which undercount once `letter-spacing` is factored in). Widths are measured with `offsetWidth`, not `getBoundingClientRect()` — the latter reports the glow animation's `transform: scale()` if one is still mid-flight, which would corrupt the measurement. A `widthFloor` variable acts as a high-water mark: normal increments only ever grow the box; `setCount` detects a *decrease* purely by comparing `next` against the previously-displayed value and only then shrinks the box snugly to fit. This is entirely client-side — the server has no notion of resets vs. increments in its broadcast (`update` covers both).
- **Reset control** — a small icon in the top-right corner reveals a value field (defaults to `0` if left blank) and a password field (`{type: 'reset', password, value}` over the same WebSocket) — lets you set the counter to any integer, useful for debugging as well as resetting to zero. The server validates the password with `crypto.timingSafeEqual` and requires `value` to be an integer (`Number.isInteger`); on success it sets the Redis counter to `value` and broadcasts `update` to everyone (so the change is instantly visible to all connected clients, not just the one who triggered it). On failure (wrong password or a non-integer value) it sends `{type: 'reset-denied'}` back to just that client, which reopens the form with an error indicator.
- **Optimistic increments/decrements** — `client.js` tracks two separate things: `serverCount` (the last absolute value the server told it) and `pendingActions` (a `Map` of its own outstanding increment/decrement requests, keyed by the `id` sent with each, each holding that request's delta). The displayed value is always `serverCount + sum(pendingActions.values())`, recomputed via `render()`. On click, an `id` is generated, added to `pendingActions`, and `render()` fires immediately (optimistic feedback) before the request is even sent. When an `update` broadcast arrives, `serverCount` is always updated to it (so other clients' concurrent changes show up immediately); if the broadcast's `id` matches one of this client's own pending entries, that entry is removed (its delta is now baked into `serverCount`, so removing it keeps the displayed sum unchanged across the reconciliation). This stays correct regardless of confirmation order — verified live against Upstash, where two rapid increments' responses actually came back in the opposite order they were sent, and the display never regressed. A prior simpler design (just re-apply `msg.count` directly on every `update`) caused a visible stutter under rapid clicking: the display would jump ahead optimistically, then briefly regress to a stale-but-correctly-ordered intermediate value before catching back up. `pendingActions` is cleared on `init` (fresh connect/reconnect — a dead connection's in-flight requests will never get a response) and on `close` (same reason, plus it prevents a stale entry from blocking future reconciliation).

## Deployment

Deploys to [Render](https://render.com) via `render.yaml` (a Blueprint: free web service, no persistent disk needed since state lives in Upstash Redis). Set `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` as secret env vars in the Render dashboard (they're marked `sync: false` in the blueprint, so Render prompts for them rather than storing values in git).
